# Unblock::HTTP1

Event-loop and operating-system neutral HTTP/1 for Perl.

Unblock::HTTP1 is a protocol engine. It does not open sockets, resolve names,
perform TLS, select an event loop, or decide connection-pool policy.

The caller gives the engine received bytes:

    $engine->input($bytes_from_transport);

The caller takes generated bytes back out:

    while ($engine->want_write) {
        my $bytes = $engine->output;
        $transport->write($bytes);
    }

If the transport reaches EOF, tell the engine explicitly:

    $engine->input_eof;

That matters for legal HTTP/1 responses whose body ends when the connection
closes.

This boundary lets the same HTTP/1 implementation work with different event
loops, frameworks, blocking sockets, in-memory transports, and other reliable
ordered byte streams.

## Message objects

Unblock::HTTP1 uses Uniform::HTTP 0.04 directly:

    Uniform::HTTP::Request
    Uniform::HTTP::Response

It does not define competing request or response classes.

Received messages preserve the exact request target, ordered duplicate header
fields, trailer fields, and the actual HTTP version. Initial metadata freezes
once parsed while trailers can continue to arrive. The complete received
message is frozen when framing reaches its end.

Application-created outgoing messages can leave version unset. The HTTP/1
engine selects HTTP/1.1 by default without rewriting the caller's object.

## Client

    use Uniform::HTTP::Request;
    use Unblock::HTTP1::Client;

    my $client = Unblock::HTTP1::Client->new;

    my $tx = $client->request(
        Uniform::HTTP::Request->new(
            method    => 'GET',
            target    => '/',
            authority => 'example.com',
        ),
        on_response => sub {
            my ($tx, $response) = @_;
            print $response->status, "\n";
        },
        on_body => sub {
            my ($tx, $response, $bytes) = @_;
            process_bytes($bytes);
        },
    );

Requests on one Client are queued serially. This avoids silently imposing
HTTP/1 pipelining policy on callers.

For a streaming request body:

    my $tx = $client->request(
        $request,
        stream_body => 1,
        on_drain => sub {
            my ($tx) = @_;
            produce_more($tx);
        },
    );

    $tx->write($chunk);
    $tx->end($last_chunk);

HTTP/1.1 uses chunked transfer coding when the length is not known in advance.
HTTP/1.0 streaming requests require an explicit Content-Length.

For received responses, Unblock removes HTTP message framing. A final
`chunked` transfer coding is decoded as framing. Any earlier transfer coding,
such as `gzip`, remains encoded in the body bytes and remains visible in the
`Transfer-Encoding` field. Unblock does not silently perform compression or
representation decoding.

## Server

    use Uniform::HTTP::Response;
    use Unblock::HTTP1::Server;

    my $server = Unblock::HTTP1::Server->new(
        on_request => sub {
            my ($tx, $request) = @_;

            $tx->respond(Uniform::HTTP::Response->new(
                status => 200,
                body   => "hello\n",
            ));
        },
    );

Request bodies arrive incrementally through on_body. on_request_end runs after
the complete request body and any trailers have arrived.

For outgoing messages with known trailers, Unblock adds a Trailer header that
announces their field names. Streaming producers that decide trailer names
later can predeclare them with an explicit Trailer header.

HTTP/1.1 TE negotiation is also handled at the wire boundary. Client requests
that contain TE are emitted with Connection: TE, and a server will only apply
a non-chunked response transfer coding that the request actually accepted.

## Informational responses

A server can emit 100, 102, 103, or another non-101 informational response
before the final response with Transaction->send_informational(). The client
receives each one through on_informational.

## Upgrade and CONNECT

HTTP/1 protocol switching is part of the engine boundary, not an event-loop
feature.

A 101 response, or a successful CONNECT response, ends HTTP framing on that
connection. The engine then reports is_switched and stops consuming bytes as
HTTP.

Bytes that followed the HTTP message in the same transport read are preserved:

    my $bytes_for_next_protocol = $engine->take_remainder;

This lets any transport or framework hand the preserved bytes to the next
protocol implementation without losing or reparsing them.

## What Unblock::HTTP1 owns

- HTTP/1.0 and HTTP/1.1 request and response semantics
- compatible handling of higher HTTP/1 minor versions using HTTP/1.1 semantics
- strict message framing validation
- request and response serialization
- Content-Length framing
- chunked transfer coding
- close-delimited response bodies
- ordered duplicate header preservation
- trailer parsing and serialization
- persistent-connection semantics
- informational responses
- streaming body production and cooperative backpressure
- Upgrade and CONNECT protocol-switch boundaries
- exact post-HTTP remainder preservation

## What it does not own

- sockets
- DNS
- TLS
- event loops
- threads or processes
- connection pools
- redirects
- cookies
- authentication policy
- proxy selection policy
- retry policy
- WebSocket framing or tunnel protocol semantics
- HTTP/2 or HTTP/3

Those belong to the caller or to a higher HTTP client/server layer.

## Native parser

The distribution vendors picohttpparser and compiles it as an internal XS
backend. Building and installing Unblock::HTTP1 does not download C source at
build time.

The XS layer is deliberately transport-neutral. Transport-specific native
consumer APIs and event-loop internals are not part of Unblock::HTTP1.
Specialized adapters can optimize byte movement without changing the portable
engine.

## Limits

Defaults are finite and configurable per engine:

    maximum HTTP head:             65536 bytes
    maximum header fields:         100
    maximum chunk extension bytes: 16384 per message
    body high water:               65536 bytes
    body low water:                32768 bytes

Set max_chunk_extension_size to 0 to opt out of that extension budget. The
native parser also has a hard ceiling of 256 header fields per parsed section.

## Development status

The distribution has not yet been released.

The portable engine has completed its planned protocol-completeness,
cross-platform, security-hardening, and benchmark passes.

Its suite exercises client/server exchanges entirely in memory so the core
cannot accidentally depend on a particular socket type, framework, operating
system, or event loop.
